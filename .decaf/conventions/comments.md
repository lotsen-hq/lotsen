# Comments in lotsen

These are lotsen's additions to the decaf comment rules (`/decaf-quality:write-comments`). Where they contradict those rules, these win.

## Scope and layout

- The doc-comment rules cover the C# XML doc comments and the TSDoc comments in `ui/`. The wording rules and the glossary apply to every language in the repository: C#, TypeScript, Svelte, MSBuild and the shell scripts that tests write.
- Comments fill lines up to 200 characters and wrap there, as code does (`max_line_length` in `.editorconfig`). Don't wrap a comment shorter than that to fit a narrower width.
- Nothing renders the doc comments, so write them for the editor. Served text is the exception.
- `comment-lint.py`, beside this file, flags wording the rules usually forbid: phrasal verbs, idioms with two readings, the passive with an agent, semicolon chains, history and references to nibs. Each hit is a candidate to judge, not an error.

## Served text

Some strings in the code reach Claude or the reviewer as text, so they are served text, not comments:

- An operation's description in `OperationCatalog` becomes the MCP tool's description that Claude reads, and the operation's description in the HTTP schema.
- A `[property: Description(...)]` on an operation input becomes that property's description in the input schema.
- A refusal's reason in an `OperationError`, an `ExternalFailureException` or an `AzureDevOpsException` reaches Claude and the reviewer as an error message.

Rules for served text:

- **Write for Claude and the reviewer.** Say what the operation does, what a value holds, or what went wrong and what fixes it, in the API's words. Leave out class names, file paths and the reasons behind the code. Put those in a comment on the code that keeps them.
- **Name the fix in a refusal.** "Run 'az login', then try again" tells the reader what to do. A reason never holds a token, a command line or a secret.
- **Describe the field, not the operation.** The operation's description already describes the operation, so a property's description does not repeat it.
- **Keep a long description on one line.** A served string may run past 200 characters, because splitting it only to fit the width makes it harder to read and to search.

## Glossary

The terms comments use with one fixed meaning. Use them as defined here, and add a term the first time a comment needs one.

| Term | Meaning |
|---|---|
| Tour | A guided walk through one review target, which Claude writes for one reviewer: a `Tour`. |
| Review target | What a tour reviews: a `TourTarget`. The only kind is a pull request, a `PullRequestTarget`, which names its platform's ID and its URL as the platform normalized it. |
| Platform | The hosting service behind a pull request, such as Azure DevOps: an `IPullRequestPlatform`. It recognizes and labels its pull request URLs, tells whether two of them name the same pull request, resolves a pull request's latest iteration, builds the web URLs of the mentions in a tour's prose and supplies the git credential for its remotes. |
| Label | The short name that a target's platform gives it, such as `contoso/shop/web #42`, or the target's URL when no registered platform names it. The tour list and the top bar show it. |
| Reviewer | The person who reads the tour in the UI. Claude is never called the reviewer. |
| Familiarity | How well the reviewer knows the code under review: familiar, some or new. It guides how much each stop explains. `create_tour` sets it. Only the UI changes it later, with `change_familiarity` or with a plan approval, and only with a bound session, because the level only guides Claude. A plan-first tour changes it only with the plan approval until the reviewer approves the plan, and keeps it while the plan approval waits. One store update stores the new level with the familiarity change, or with the plan approval. |
| Familiarity change | The reviewer decision that a change of the familiarity level reports: a `ReviewerDecision.FamiliarityChanged`, of kind `familiarityChanged`, in a decided thread, with the earlier level, the new level and the stops to rewrite at it. The stops to rewrite are those after the stop under view, or every stop when none is open, that have content and no skip. Only `change_familiarity` builds one, and it waits alone with the plan approval. It never goes again with a re-send. The reviewer asks again at the tour's current level, after Claude declined the last question in the latest one's thread or that question was canceled or unanswered, and the new one keeps the earlier level and picks the stops from the stop under view then. |
| Plan | A tour's chapters and stops, in tour order. Claude sets the plan before it writes the stops' content. |
| Plan first | The `create_tour` option under which the plan waits for the reviewer's approval before any stop is written: `Tour.PlanApproval`, awaited from the tour's creation, given once the reviewer approves. While a plan is set and the approval is awaited, the plan waits: `put_stop` is refused and `set_plan` still revises the plan. A tour without the option never waits, and an approved plan never waits again. |
| Plan approval | The reviewer's approval of a waiting plan, from the UI's `approve_plan`, which needs a bound session. One store update stores the reviewer's skips and level, gives the approval and reports it as a `ReviewerDecision.PlanApproved`, of kind `planApproved`, in a decided thread, with the proposed order, the skips and the level, and the reviewer's optional words as the thread's question. A cancel or a lost request leaves the plan approved, and the decision goes again with a re-send only while no stop has content and the tour still holds the decision's level, skips and stops. |
| Chapter | A named group of consecutive stops in a plan. |
| Stop | One step of a tour, as the plan announces it: a `Stop.Pending` without content, or a `Stop.Written` with its content, its version number and its earlier stop versions. A stop has a kind (overview, context, inspect, risk or question), and its status follows from its stage and version: pending, ready at version 1, revised from version 2. A stop owns its earlier versions, its stale marker and its skip. |
| Stop content | What a stop says and the code it points at: a `StopContent`, with a headline, optional prose fields, checks, tags, a placement hint and its passages. `put_stop` writes it as the stop's next stop version. |
| Check | One decision that a stop's content asks the reviewer to make: a `StopCheck`, with a question and an optional recommendation, both prose, and optional suggested answers. The server gives each new check an ID unique within the tour, and a check that Claude writes again with its ID keeps it. A question stop has at least one check. A stop text anchor names a check's prose by the check's ID, as `checks[<check ID>].question` or `checks[<check ID>].recommendation`, so a reorder of checks moves no anchor. |
| Stop version | One content of a stop, numbered from 1. A `put_stop` on a stop with content is a revision: it stores the new content as the next version and keeps the replaced one as an earlier version, a `StopVersion` in the written stop's `Earlier`, oldest first, with the stop's title and kind at that time. An agent session's reads of the tour leave the earlier versions out and keep the version number. A `set_plan` that drops a stop drops its earlier versions with it. |
| Stop under view | The open stop, which the Stop panel and its inline block show. A revision of it keeps the stop version that the reviewer reads on screen, read-only, with a banner that shows the new one. The reviewer can also open an earlier stop version of it read-only. Opening another stop or tour shows the current version again. |
| Open stop | The page's state of one tour's stop under view, derived from the tour record and the pin: which stop is open, the stop version that it shows, its passages at the pin, the focused passage and whether it is stale. An `OpenStop` in `ui/src/lib/openStop.svelte.ts`. The page keeps the stop version that the reviewer reads through a revision that the reviewer did not ask for, as `OpenStop.applyPlan` says. |
| Reading progress | The place that the reviewer opened last in a tour, a stop or the summary page, and whether the reviewer has opened the summary page: a `ReadingProgress` on the tour. Only the UI records it, with `record_reading_progress`, with or without a bound session, and no session event tells of it. Opening the tour from the tour list resumes there. |
| Tour state | Where a tour is in its life, which the server derives and the tour list shows: generating, ready, in progress, finished or archived, a `TourState` from `TourStates.Of`. Generating while the tour has no plan or a pending stop, ready once every stop has content, both until the reviewer opens a stop or the summary page. In progress once the reviewer opened a stop, finished once the reviewer opened the summary page, whatever Claude writes later. Archived while the reviewer keeps the tour archived, with `set_tour_archived`, and unarchiving returns the derived state. The event `tourStateChanged` carries each change, with the tour's pull request state. |
| Hidden tour | A tour that the tour list leaves out until the reviewer shows hidden tours: an archived tour or a flagged tour, as `hiddenReason` in the UI decides. A tour that is both counts once. |
| Pull request state | Whether a tour's pull request is active, completed or abandoned, as the last iteration check learned it from the platform: a `PullRequestState` on the tour, active until a check learns another. Each platform maps its own states onto these, and a state that lotsen does not know counts as active. A check stores it whatever the pin, and so does an iteration update that the platform's answer refuses. Each stores it only while the tour holds the state that it read before it asked the platform. The event `tourStateChanged` carries each change. |
| Flagged tour | A tour whose pull request state is completed or abandoned. The tour list shows "PR completed" or "PR abandoned" and hides it by default. Nothing archives or deletes it, and a check that finds the pull request active again clears the flag. |
| Skip | The reviewer's mark that they pass over a stop of the plan, pending or with content: the stop's `Skipped`. Only the UI skips a stop or takes the skip back, with `set_stop_skipped`, with or without a bound session, and no session event tells of it. A skip is not private, so an agent session's read of the tour shows it. Next and back in the stop navigation pass over a skipped stop, and the reviewer can still open it. A `set_plan` that leaves the stop out drops its skip. Never call a skip a review mark. |
| Outdated answer | An answer whose check a revision dropped or gave a new ID: a `CheckAnswer` with `OutdatedOn`, the number of the earlier version that it stays on. It keeps its answer state, so an outdated draft stays the reviewer's own. No send holds it, the unsent count leaves it out, and no write reaches it. |
| Suggested answer | An answer to a check that Claude expects the reviewer to give: a `SuggestedAnswer`, with plain text, never prose, and an answer type. The UI shows it without its type. Say "suggestion" for short. |
| Answer type | What kind of answer the reviewer gives to a check: decision, concern or open question, an `AnswerType`. Claude types each suggested answer. |
| Answer | The reviewer's answer to one check: a `CheckAnswer`, with plain text, an answer type and an answer state, which the tour holds at most once for each stop ID and check ID. The reviewer picks a suggestion, which gives the answer its type, or writes the answer, which keeps the type of the check's earlier answer, or starts as a decision when the check has no answer. Only the UI writes, retypes and clears an answer, with or without a bound session, and only for a check of the stop's current content. An answer stays stored when a revision drops its check or gives it a new ID, and its check ID stays used. It is then an outdated answer. |
| Answer state | How far an answer has come on its way to Claude: draft, sent or received, an `AnswerState`. A draft answer is one that the reviewer has not sent, and an agent session's reads of the tour leave it out. A change to the text or type of an answer makes it a draft again, whatever its state. |
| Batch | The answers that one `send_answers` sends to the bound session together, under one batch ID: an `AnswerBatch`, which each of its answers holds with the ID of the session it went to. The session gets one session event for the batch, with the IDs alone, and reads the answers with `fetch_answers`. A batch holds every draft answer to a check of the plan's current content, and every sent answer whose session lost the tour or ended before it received the batch, or none. A changed or cleared answer leaves its batch. Say "note batch" for the notes that one `send_notes` sends. |
| Sent | Said of an answer that a batch holds and that the batch's session has not fetched yet. |
| Review summary | What the review of a tour has produced so far, which the server builds from the tour's state alone: a `ReviewSummary`, from `read_summary`, which any caller reads, with or without a bound session. It groups the answers by answer type with the outdated answers apart, lists the plan's risk stops as concerns, groups the threads by thread state, notes and tour actions included, and names the skipped stops and the stale stops in plan order. An agent session's summary comes from the tour that `AgentView.For` returns to it, so it holds no draft answer and no note. It also holds the tour's synthesis, if any, and for every caller the fingerprint of the agent session's summary. |
| Synthesis | The bound session's prose on what the review decided, what worries the reviewer and what stays open: a `TourSynthesis`, which `write_synthesis` stores on the tour in place of the last one, with its write time, the pin its `ref:` links were checked against, and the fingerprint of the review summary that the session read before it wrote the synthesis, as the session passes it. The review summary returns it with whether it predates the summary: the fingerprint of the agent session's summary differs from that one. The fingerprint holds the pin's merge base and head, and a fetch of a batch, a draft answer, a note and the thread of a summarize tour action or a follow-up action never change it. The summarize tour action asks for one, and its reply only reports it. |
| Follow-up action | A tour action from the summary page that hands the bound session one group of the review summary: `draftWorkItems` the decisions, `walkOpenQuestions` the open questions, `draftComments` the concerns with the risk stops, a `TourAction.FollowUp`. Its request names only its kind. `ActionRules.Admit` collects its items from the agent session's summary when the server stores the request, so they hold no draft answer, and a re-send carries the same items. A group without an item is refused with the reason that the summary returns for the page. lotsen acts on no item: Claude creates work items and posts comments with its own tools after the reviewer approves in the terminal, and starts a thread for each open question. Not a follow-up, which is a question in a thread. |
| Summary page | The page that the center shows after the plan's last stop, in place of a stop and a file: the tour's review summary, with each answer, risk stop, thread and stop linked to its stop, its check or its thread. Next on the last stop that is not skipped and the Plan panel's Summary entry open it, and back goes to the last stop that is not skipped. It loads the summary again on each event that can change it, and has its own history entry. |
| Passage | In a stop's content, lines of one file at one side that the stop points at: a `StopPassage`, with its 1-based start and end line, its role and the text the server read at the side's commit. Never call a hunk's line range or a `TextChange` a passage. |
| Primary passage | The one passage of a stop's content that the stop is about. The other passages are related passages. The primary passage of an inspect, risk or question stop must touch the diff. |
| Touches the diff | Said of a passage that overlaps a changed region of its side in the file's diff, or borders a region that is empty on that side, where the other side's lines go: `DiffTouch.Touches`. |
| Prose | The restricted Markdown that a tour's text is written in: paragraphs, lists, emphasis, inline code, code blocks and links, with no raw HTML or images. `ProseRenderer` renders it to HTML. |
| Prose field | One field of a stop's content that holds prose: the headline, how, why, the design choices, pinned by, the scenario, or a check's question or recommendation. A `ProseField` names it by its path, such as `checks[<check ID>].question`, and `StopProse` is the one definition of the fields. |
| Code reference | The lines of one file at one side that a `ref:` link in prose points at: `CodeReference`. The link reads `ref:<side>/<path>#L<start>-<end>`, with the repository path percent-encoded and both lines 1-based. |
| Mention | A link in prose to a work item or to a pull request in the tour's repository, which Claude writes with a scheme of its own, `[#1234](workitem:1234)` or `[!42](pullrequest:42)`. `MentionLinks` reads it, and the platform of the tour's pull request builds its web URL. A bare `#1234` in the text is no mention. |
| Anchor hint | The plan's guess at where a stop will point: a repository path and an optional 1-based line. A stop's own passages replace it. |
| Repository path | A file's path inside the repository, with forward slashes, no `.` or `..` segments and no leading slash: `RepositoryPath`. Anchor hints, stop content, file marks, code and file anchors and the file API check paths with the same rule. |
| Pin | Whether a tour is fixed to the commits of its pull request, as a `TourPin`: pinning, pinned or failed. Say "pin state" where the bare word could mean the act of pinning. |
| Pinning | The background job that asks the platform for the pull request's latest iteration, syncs its clone and computes the merge base. Also the pin state of a tour while that job runs. |
| Pins | The commits a pinned tour shows: its merge base, its head and the iteration they came from. Every later view and check reads them. |
| At the pin | Said of lines that a passage or a code or file anchor read at the pin's commit of their side: the merge base at the base, the head at the head. A stale stop's passages and an anchor that an iteration update could not move stay on an earlier commit, so the UI neither marks them in the diff nor opens them there. Without a pin every commit counts. |
| Merge base | The merge base of the iteration's source and target commits. The tour shows the pull request as the diff from the merge base to the head. |
| Head | The source commit of the iteration a tour is pinned to. |
| Iteration | One version of a pull request: the head and target commits its platform reports after a push. Azure DevOps numbers them as iterations. A tour pins the latest iteration when pinning runs. |
| Iteration number | The platform's number for an iteration, from 1: `ResolvedPullRequest.Iteration`, which a pin, a stale marker and the decided thread of an iteration update carry. It rises by at least one with each change of the source head, a change back to an earlier head included, and never falls for one pull request. A platform without native numbers counts the changes of the source head that it has resolved for the pull request. `PlatformContractTests` checks the promise on every adapter. |
| Iteration check | The server's check of whether a pinned tour's pull request has a new iteration, one whose source commit differs from the pinned head: an `IterationLifecycle.CheckAsync` run that the iteration scheduler starts, decided by `IterationCore.Check` on the latest tour under the writer's lock. A new target commit alone is no new iteration. It never changes the tour's pin, and a failure keeps the last result. It also stores the pull request state that the platform reported. |
| Available iteration | The new iteration that the last iteration check found, stored on the tour: an `AvailableIteration`, with the pin the tour would have on it and the IDs of the stops that an update to it marks stale. It names no pin to compare with: only a pinned tour holds one, and the iteration update that changes the pin clears it in the same store. A check that finds the pinned head again clears it too. |
| Iteration update | The reviewer's move of a pinned tour onto its available iteration, from the UI's `update_iteration`, which names the pin that the page's notice showed and needs a bound session. It is refused while the tour's available iteration is another one. It is a `Repin` that `IterationCore.Update` builds from the latest tour, stored in one store update with the re-pin. It asks the platform nothing, so a newer head becomes the next available iteration. `Repin` says which stops and anchors move. Every stop with content that does not move gets a stale marker, and every open thread whose anchor is stale becomes outdated unless its last question waits. When a stop is stale, the same store update reports the update as a `ReviewerDecision.IterationUpdated`, of kind `iterationUpdated`, in a decided thread with the iteration's number and the IDs of the stale stops. It never makes the plan wait for approval again. |
| Stale marker | A stop's `StaleOn`: the number of the iteration whose update made the stop's content stale. The content keeps its passages and code references on the pin before that update, and an update after it leaves the stop as it is. The stop's next `put_stop` clears it. It is no stop status: the status follows from the version alone. |
| Remap | The computation that maps a pinned tour's passages, code references, thread anchors and file marks onto the pin of a new iteration: `TourRemap`, a pass over git facts that reads no git. A file mark follows a rename between the heads. Each line range maps through git's diff of its file from the commit it was read at to the new commit of its side, and moves when no hunk touches its lines. It stores nothing. |
| Git fact | The answer to a question about named commits, keyed by a `FactKey`, such as the changed paths between two commits or the hunks of a file's diff. Commits are immutable, so a fact never changes once read. A `FactSet` holds facts by key, and a missing fact is no answer. |
| Fact memo | The facts that the server read so far, a `FactMemo` up to a budget of their estimated sizes, which evicts the least recently used. A restart empties it. The fact cache size sets the server's budget. Served text and the docs call it the git fact cache. |
| Fact cache size | The fact memo's budget in whole mebibytes, from 1 up, that the user chooses with `serve --fact-cache-mb` or the `LOTSEN_FACT_CACHE_MB` environment variable: a `FactCacheSize`. The option wins over the variable. Without either, it is 64. |
| Fact scope | An `IFactScope`: a clone use with reads of git facts from one clone, which opens the clone at most once, on its first call that needs git: a read of a fact that the memo lacks, a download of the changed files or `OpenCloneAsync`. |
| Iteration core | `IterationCore`: the pure decisions of the first pin, the iteration check and the iteration update, from a tour, a platform answer and git facts. A pass that lacks facts returns the keys it needs, and the caller reads them and runs the pass again. |
| Iteration scheduler | `IterationScheduler`: decides when each tour's iteration check runs, one at a time per tour, from nudges, a debounce, an interval for reusing the platform's answer, a poll of the tours the reviewer read lately, and a backoff after failures. |
| Nudge | A reason for a tour's iteration check to run, which the iteration scheduler receives: a `Nudge`, such as a reviewer read or a store that changed the stops under an available iteration. |
| Stale | Said of a passage, code reference or anchor that the remap cannot move: a hunk changes its lines or inserts lines between them, its file is gone or unreadable at the new side, a rename gives its file a path that `RepositoryPath` refuses, or, for a change stop's primary passage, it no longer touches the diff. It keeps its old place. A stale stop is a stop with a stale passage or code reference. A pending stop and an earlier stop version are never stale. |
| Side | `base` or `head`: which of a pinned tour's two commits a file is read at. `base` names the merge base. |
| Commit ID | A git object's full hash in lowercase hexadecimal, 40 digits with SHA-1 and 64 with SHA-256: `CommitId`. An abbreviated hash is never a commit ID. |
| Clone | The server's own blob-less partial clone of a repository, in the data directory. The clone cache keeps one per remote URL. The server never reads the user's working copy. |
| Temporary clone | A clone in progress, under the clone's name with a process ID and `.tmp`, which the clone cache renames to the clone's name once git finishes. A process killed during its clone leaves one. |
| Clone use | A `GitRepository` that `CloneCache.OpenAsync` returned, from before its open starts until it is disposed, or a `CloneCache.Hold`, which runs no git. A pin, a fetch, a fact scope and every file read hold one. A pin and an iteration check keep their fact scope until they stored what refers to the clone. A prune never removes a clone in use, nor one whose last use ended while the prune ran, and maintenance never runs on one. A use that starts during maintenance runs no git until the maintenance ends. |
| Prune | The removal of the clones that no tour refers to, with the temporary clones that no clone in progress owns: `CloneCache.PruneAsync`. A tour refers to the clone of each tour remote that `TourRemote.Of` lists for it, and a tour stored with another schema version refers to none. While any other tour cannot be read, a prune removes nothing. A prune leaves a clone that a clone use or maintenance holds. `delete_tour` prunes the deleted tour's clones after it answers, and `prune_clones` prunes them all. A canceled prune stops between two clones. |
| Tour remote | A remote that a tour uses, with its platform's git credential: a `TourRemote`, which only its own factories build. `TourRemote.Of` lists a tour's remotes, those of its pin and its available iteration, and the clone cache opens only a tour remote, so a prune keeps the clone of every remote that an opener stores. |
| Clone lock | The lock of one clone that its opens take for a clone or a fetch, so those run one at a time. Queries take no lock. The clone cache keeps it only while a clone use or maintenance holds the clone. |
| Ref lock | A file that git creates, and fails to create when it exists, to update a clone's refs: `<ref>.lock` under `refs/`, `HEAD.lock`, `packed-refs.lock`, and the `packed-refs.new` that git writes under that lock. A killed git leaves its ref locks. Before each fetch, under the clone lock, the clone cache deletes those that git last wrote more than `CloneCache.StaleRefLockAge` ago. It keeps each younger lock, whether a live git that the cache did not start or a git killed within that time left it. |
| Maintenance | Git's `maintenance run --task=gc` on one clone, which `CloneCache.MaintainAsync` runs once a day for each clone, only while no clone use holds it. `CloneMaintenance` starts a run every ten minutes and after each prune. Git's own automatic maintenance is off in every git run of the server. |
| Deleted tour | A tour that the reviewer removed for good with `delete_tour`, which only the UI calls. Its file is gone, every page drops it on the `tourDeleted` event, and every later write of it stores nothing, because `ITourStore.Update` finds no tour. |
| Remote URL | The URL a clone fetches from, without user info. The pin stores it, so the file API can open the tour's clone. |
| Changed file | A file that differs between a tour's merge base and head, with its change kind: added, modified, deleted or renamed. A renamed file carries its path at the head and its old path at the merge base. |
| Binary file | A file whose blob on a side git treats as binary, because a NUL byte appears in its first 8000 bytes. The file operations return none of its content. |
| Large file | A file whose blob on either side is larger than `FileOperations.LargeFileSize`. The file operations return its content only when the caller includes large files. |
| Line-endings-only file | A modified or renamed text file, its mode unchanged, in which git finds no changed line when it compares lines without the carriage return before each line feed. The changed-file list marks it, and the viewer collapses its diff. |
| File mark | Claude's mark in the plan on a file whose change needs little review, mechanical or generated, with a one-line reason: a `FileMark`. The viewer collapses a changed file that has one. The server does not check that the pull request changes the file. |
| Review mark | The reviewer's mark that a changed file is reviewed, with the object ID of the version of the file that the reviewer saw, as the changed-file list gave it: a `ReviewMark`. It counts only while the file at the pinned head has the same object ID, or for a deleted file, while the file stays deleted. The tour's file holds the marks beside the tour, and no agent tool reads or writes them. Never call a file mark a review mark. |
| Ignore whitespace | The diff option `DiffWhitespace.Ignore`: a line that differs from the other side only in whitespace or in its line ending counts as unchanged. The texts stay the same. The reviewer's choice is a preference, like the layout. |
| Text change | One range that differs between the base text and the head text of a file, as UTF-16 offsets into each text: `TextChange`. It has the shape of a `Change` in `@codemirror/merge`. |
| Access token | The token for a platform's API and git remotes that a token provider returns. It lives in memory only and reaches git only through environment variables. Never call the server token an access token. |
| Token provider | An `IAccessTokenProvider`: what a platform's git credential and its client ask for an access token, with the validity that the call which sends it needs. Each platform supplies its own. The Azure DevOps provider runs the Azure CLI. |
| External failure | A failure outside the process: a platform's request, a credential, a git call, or a remote URL that lotsen does not clone from. An `ExternalFailureException`, whose subtypes only Core declares. A site that turns one into a result catches the base type and serves its reason, and any other exception is a fault of lotsen that propagates. |
| Git credential | An `IGitCredential`: what git presents to a platform's remotes, which the platform supplies with its scheme and its fix hint. `GitRunner` asks it only when a remote asks git for authentication, and tells the answer's source when the remote refuses it, as a `GitAuthException`. |
| Server | The long-running process that holds every tour and serves the API and the UI: a foreground server, which `lotsen serve` runs until Ctrl-C or `lotsen stop`, or a background server. |
| Background server | A server that the adapter starts on demand when none runs, as the hidden `lotsen daemon` command: `BackgroundServer`. It runs in a session and process group of its own, logs to the log file, and exits once no agent session has been open for its grace period. Its agent sessions are its clients. A browser page is not a client. |
| Grace period | How long a background server waits with no agent session open before it exits: 60 seconds, counted from its start or from the drop of its last session. A session that opens during it cancels the exit. `AgentSessions.ExitWhenIdle` decides the exit under the lock that every session open takes, and refuses every session from then on. An adapter of another build ends it at once, through `AgentSessions.TryExitNowWhenIdle`. A foreground server has none. |
| Shutdown route | `POST /api/shutdown`, which takes the server token alone and stops the server as Ctrl-C does, after it answers: `ShutdownEndpoint`. `lotsen stop` and `lotsen restart` call it through `ServerShutdown`, then wait until the server's process has exited. Say "shutdown" for the request, because a stop is a step of a tour. |
| Log file | `server.log` in the data directory, user-only: `ServerLog`. A background server empties it once it holds the claim lock and writes the lines that the console gets for `lotsen serve`, so it holds no credential. A start that fails adds its reason at the end, which the adapter's error quotes. |
| Adapter | The `lotsen mcp` process that Claude Code starts. It serves MCP over standard input and output and forwards each tool call to the server. It starts a background server when none runs. |

| UI contract | The JSON shapes that the UI sends and receives, written from the C# types: the schema document `ui/src/lib/contract.schema.json` from `UiContract`, and the TypeScript types `ui/src/lib/contract.generated.ts` from that document. `just contract` writes both, and `just check` fails while either differs from the code. |
| Golden fixture | One sample of an event payload or of an operation's output, as the server's serializer writes it for the UI: `ui/tests/contract/fixtures.generated.ts`, which `ContractTests` writes from `ContractSamples`. The UI's type check checks it against the UI contract, and the UI's tests feed it through the UI's own code. |
| Whole-repository view | The file tree beside the changed-file tree that lists every entry of the repository at one side, one directory at a time. A changed file opens its diff from it, and an unchanged file its text at that side. |
| Layout | How the diff view shows a file: side by side, with a `MergeView`, or inline, with `unifiedMergeView`. |
| Row | One height position of a diff's layout: a `RowLayout` row. Side by side, a row pairs the lines the two panes draw at the same height; inline, a row is one head line or one deleted line. |
| Collapsed region | A run of rows away from the open stop's passages that the diff hides behind a marker saying how many lines it hides. The reviewer expands it in steps or whole. |
| View mode | How the viewer shows a stop, a reviewer preference that is not part of the tour: the whole pull request, with the lines outside the stop dimmed in the diff, stop files, or step through. Each tour opens in the default from the settings, and a mode the reviewer chooses lasts until another tour opens. |
| Stop files | The view mode that stacks the open stop's files in the center, in step through's order of their passages, each collapsed to its passages. A passage, a code reference or a file that the reviewer opens from outside the stop joins the bottom of the stack, marked as outside the stop, until the stop or the tour changes. Another view mode hides it, and the history entry keeps it, so it shows again when the reviewer returns to stop files. |
| Step through | The view mode that shows one of the open stop's passages at a time: the primary passage first, then the related passages in Claude's order. |
| Diff toolbar | The row at the top of the center column: the view modes, step through's passage navigation, the open file's path or the count of stacked files, the diff options and the panel's actions. Each stacked file shows its path in a header of its own. |
| Stop bar | The one-line bar that overlays the top of the Stop panel once the full header and notices have scrolled away: the kind, the title and one truncated line per notice. It repeats the header, so it holds no controls and is hidden from screen readers. |
| Send row | The row at the end of a stop's Checks section that shows the tour's unsent count and sends the same single batch as the top bar. |
| Seen version | The newest version of a written stop that the reviewer has seen. It only goes up, stays out of Claude's view, and decides the Plan panel's Revised marker. |
| Focused passage | The passage the reviewer opened last, or the primary passage before one opens or when the stop's passages no longer hold it. Step through shows it alone, and in every view mode the prose highlights the `ref:` links that point into it. |
| Hovered reference | The code reference of the `ref:` link in the open stop's prose or in a reply that the pointer is over, or else the one with visible keyboard focus. The diff highlights its lines where it shows the file. |
| Pane split | The base pane's share of a side-by-side diff's width, which the splitter between the panes sets: a `PaneSplit`. Every side-by-side diff on the page shows the same split. It is a preference, which a page reads once, when a diff first shows it. |
| Workspace | The page's area below the top bar, where Dockview arranges the panels Files, Plan, Code, Stop and Threads, each named by a `PanelId`. `Workspace.svelte` mounts each panel as a Svelte root of its own and hands its element to Dockview. |
| Group | A Dockview group of the workspace: one or more panels as the tabs of one tab row. Its header holds the Maximize, Pop out and Hide buttons of its active panel, and no buttons in a popout window. |
| Workspace layout | How Dockview arranges the workspace's groups, which a `WorkspaceLayout` changes through Dockview's API. Not the diff's layout. The page saves it only after a change that the reviewer makes, so the Default layout that a load falls back to stays unsaved. |
| Arrangement | A ready-made workspace layout that the Panels menu applies: Default, Columns or Explanation above the diff, an `ArrangementId` in `ui/src/lib/arrangements.ts`. Each is a layout record built in code with every panel shown, and Reset layout applies Default. |
| Named layout | A layout record that the reviewer saved under a name, which the Panels menu's My layouts group applies: a `NamedLayout` in `ui/src/lib/namedLayouts.ts`. Each is the value `{ name, record }` under its own key of the preference store, `workspaceLayouts/<id>`, in a preference family. A rename keeps its id and every other member of its value as stored. One whose record the page cannot read, such as one that a later version saved, shows disabled. Another page's change updates the menu and never applies the layout. |
| Layout record | A workspace layout as the page keeps it: a `LayoutRecord` in `ui/src/lib/layoutRecord.ts`, with Dockview's serialized layout, the hidden panels and the group that each one goes back to, under a version number. The saved layout, the ready-made arrangements and the reviewer's named layouts all take this form. It holds no popout window: a panel in one is in its place in the main window, as `withoutPopouts` puts it. |
| Hidden panel | A panel that the reviewer hid from the Panels menu or with its group's Hide button. It sits alone in a group that Dockview hides, so it stays mounted. A maximized group hides the other groups without hiding their panels. |
| Popout window | A browser window of its own that shows one panel of the workspace, opened from its group's Pop out button: a Dockview popout group, whose page is `popout.html`. The page's one app runs it, and closing the window returns the panel to its place in the main window. A load of a layout record closes it, or closes it once it has opened when it was still opening, a hide of its panel closes it before the panel hides, and the workspace refuses a tab dragged between it and another window. `WorkspaceLayout.poppedOut` holds which panels show in one. |
| Panel document | The document that holds a workspace panel's element now: the main page's, or a popout window's while the panel is popped out. A `PanelDocument` in `ui/src/lib/panelDocument.svelte.ts`, which the workspace moves along after Dockview moves the panel, and which `panelDocument()` gives the panel's components. A component in a panel reads the selection and the focus, listens and observes there. A menu, tooltip or dialog in a panel closes when the panel moves to another document, and locks the page's scroll only in the main page. |
| Realm | The JavaScript globals of one window, the main page's or a popout window's. A node or an event belongs to one realm, and `instanceof` against another realm's class, such as the main page's `Element`, is false for it. `isElement` and `isHTMLElement` in `ui/src/lib/dom.ts` check a node of any realm. |
| Portal target | The element at the end of a panel document's body that the panel's menus, tooltips and dialogs render into, as bits-ui portals. Each panel has its own, which moves with the panel between the main page and a popout window. |
| Placement | Where a stop's explanation shows: in the Stop panel, or inline in a block below its primary passage in the diff. The reviewer's placement mode is side, inline or mixed. In mixed mode the reviewer's per-stop move wins, then Claude's `placement` hint, then a rule. A stop without a primary passage always shows in the Stop panel, and an inline stop shows there too while no editor shows its block. |
| Explanation view | The page's one explanation of the stop under view: what it shows, where it belongs by its placement, and where it shows now, inline once an editor shows its block or else in the Stop panel. An `ExplanationView` in `ui/src/lib/explanationView.svelte.ts`, which `ExplanationBlock` renders in either host. Its inline passage is the primary passage at the pin that its inline block sits below, while it belongs inline. |
| Editor surface | What the page asks of the editors of one file: decorations, a focused line, an inline block, a selection's lines. An `EditorSurface` in `ui/src/lib/editor/surface.ts`, which `CodeMirrorSurface` implements. Only `ui/src/lib/editor/` imports CodeMirror. |
| Syntax color family | A set of syntax colors for the diff editors, a reviewer preference from the settings: Lotsen, Visual Studio Code or Visual Studio. Each has a light and a dark palette, and the theme picks between them. |
| History entry | An entry in the browser's history that the viewer adds when the reviewer opens a tour, opens another stop, opens the summary page, follows a `ref:` link or opens a file from the Files panel. Its URL fragment names the tour, the stop, the open file at its side, and the lines of the passage or code reference that opened the file, or else the summary page, which back, forward and a reload restore. Its state holds the files added to the stop-files stack, which back, forward and a reload restore too, but a link opened in a new tab does not. Other changes rewrite the current entry. It never holds a one-time code. |
